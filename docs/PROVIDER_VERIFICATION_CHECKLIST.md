## Resend

Current state: `EMAIL_MODE=disabled`, no usable `RESEND_API_KEY`, no configured sender, and no verified sender-domain/account evidence. No provider message was sent during this milestone. Customer-wide sending is not implemented in this development release.

1. Identify an authorized Resend account and approved sender. A custom sender domain must be verified with the provider's actual records. **Do not add or change production DNS during this milestone.** An existing verified sender can be inspected; otherwise domain verification remains a separate blocked action. Any provider-supplied test sender must be confirmed compatible with the actual account and official test recipients before use.
2. Provision a key through secure provider/Worker controls, never chat. Store it as `RESEND_API_KEY` on the preview Worker only. The current implementation both sends `POST /emails` and reads `GET /emails/<id>` for delivery feedback; verify access to both operations. Do not assume a sending-only credential can retrieve status. No key permission has actually been verified yet.
3. Only for a bounded authorized provider test, use `EMAIL_MODE=resend_test`, the approved `EMAIL_FROM`, and one official recipient such as `delivered@resend.dev` or `bounced@resend.dev`. The transport validates that recipient allowlist and redirects notices to it; it never sends to stored guardian addresses. Test messages consume the provider's normal account quota; no paid upgrade is authorized. Restore disabled mode after testing.
4. Exercise both English and Mexican Spanish confirmation/cancellation/refund representations with synthetic details. Check HTML escaping, chosen locale, shared booking facts, receipt/privacy boundaries, deduplication, lease/retry behavior and suppressed/anonymized notices. Local tests cover rendering and mocked transport; real provider acceptance is separate.
5. Record provider message ID, accepted state and subsequent actual delivered/bounced/complained/suppressed feedback separately. `accepted` is never reported as delivered. Inspect feedback with the existing authenticated retrieval/polling path and provider dashboard.

There is currently **no Resend webhook receiver** in this repository. Do not register a guessed callback. If inbound webhook feedback is later required, first add and verify a narrowly scoped endpoint with raw-body signature validation, provider signing secret, timestamp/replay protection and idempotent event handling. Current provider verification can use the implemented polling mechanism. A mocked payload is not provider-delivery evidence.
